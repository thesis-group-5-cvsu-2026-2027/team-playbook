02 Git in one picture

Three places a file can live. Ninety percent of Git pain comes from forgetting which one you're in.

Never git add -A blindly. Run git status first. Confirm no .env, vendor/, node_modules/, or database.sqlite sneaks in — those must never be committed. Our project's .gitignore handles them; your job is to verify.

03 Branching strategy

One long-lived branch. Everything else is short-lived and deletes on merge. No exceptions, no "I'll just commit to main real quick."

main

The deployed truth. Always green. Only merges from reviewed pull requests. Never push directly to main.

feature/*

New functionality. Branches off main, merged back via PR. Deleted after merge.

fix/*

Bug fixes. Same lifecycle as feature/*, just a different prefix for at-a-glance signal in the PR list.

docs/*

README, doc updates, comments. Rarely touches code. Safe to review fast.

Branch naming — always include your name

Prefix the branch with your last name so it's obvious who owns it in a shared repo with four contributors. When a branch sits for weeks, "feature/payments" tells nobody anything. 

# Format: {type}/{yourname}-{what}
feature/carbonell-rule-engine
feature/cedro-payment-models
fix/longakit-login-redirect-loop
docs/perez-testing-checklist

Starting a new feature

# 1. Always start from an up-to-date main
git checkout main
git pull origin main

# 2. Create your branch
git checkout -b feature/carbonell-rule-engine

# 3. Do the work, commit as you go, push when ready for review
git push -u origin feature/carbonell-rule-engine
Good branch lifetime: 1–3 days. If yours is older than a week, break it into smaller branches. The longer a branch lives, the more painful the eventual merge.

04 Commit messages that help

Commit history is a diary the whole team reads. Make it readable. We use Conventional Commits.

Format

# Subject line: {type}({scope}): {what changed}
# Blank line
# Body: WHY it changed, not WHAT (the diff shows what)

feat(auth): add RBAC middleware and forced password change

- EnsureUserHasRole checks role + is_active
- EnsurePasswordIsChanged redirects to /password/change on first login
- Seeded 4 test users with must_change_password=true for staff roles

Allowed types

TypeUse forExample
featNew user-visible functionalityfeat(payments): record partial payments
fixBug fixfix(auth): rate limiter not clearing on success
testAdding or fixing teststest(login): cover inactive user rejection
docsDocumentation onlydocs(readme): setup instructions for postgres
refactorCode restructure, no behavior changerefactor(user): extract dashboardRoute helper
choreDeps, config, toolingchore: upgrade to Laravel 13.36
styleFormatting onlystyle: apply pint to auth folder

Anti-patterns to avoid

❌ "fix" — tells nothing.
❌ "final", "final v2", "really final" — the diff already shows history.
❌ "asdf", "wip" — squash before pushing, or write something real.
❌ "Change: Env Changed" — what env? why? which values?
Rule of thumb: if your commit message can't answer "what changed and why", it's not ready. Six months from now, git log --oneline should be readable as a project timeline.

05 The daily development loop

Every work session follows the same five steps. Don't skip step one.

01
Sync

Pull main and rebase your branch onto it. This is the morning ritual.

02
Branch

Create or check out feature/yourname-what. Never work directly on main.

03
Build

Small commits as you go. Run php artisan test before every commit.

04
Review

Push, open a PR, tag a teammate. Address feedback in new commits.

05
Merge

Squash-merge into main. Delete your branch. Pull main on your local.

Step-by-step commands

# ─── Step 1: Sync ───
git checkout main
git pull origin main

# ─── Step 2: Branch ───
git checkout -b feature/carbonell-rule-engine

# ─── Step 3: Build ───
# ... edit files in VSCode ...
php artisan test                # all green before committing
git add app/Models app/Services
git status                      # verify ONLY what you intended
git commit -m "feat(rule): implement 12-month standing computation"

# ... more edits, more commits ...
git push -u origin feature/carbonell-rule-engine

# ─── Step 4: Review ───
# Open PR on GitHub → assign teammate → address comments → push fixes

# ─── Step 5: Merge ───
# Click "Squash and merge" on GitHub
git checkout main
git pull origin main            # your local main is now updated
git branch -d feature/carbonell-rule-engine
If git pull origin main conflicts on your feature branch: git rebase origin/main. Fix conflicts in your editor, git add the resolved files, git rebase --continue. Never git merge main into your feature branch — it pollutes the diff with main's commits.

06 Pull requests & reviews

A pull request is a conversation, not a formality. The reviewer's job is to prevent broken main, not to approve fast.

Before you open a PR

  • Branch is rebased on the latest main (no merge commits)
  • php artisan test passes locally — all 35+ tests
  • New behavior has at least one new test
  • No dd(), dump(), var_dump(), or console.log() left in
  • No .env, vendor/, or DB files in the diff
  • Commit messages follow the format from section 04

PR template

## What
Implements the rule-based account standing algorithm (FR-21 to FR-25).

## Why
Needed so payments module can check eligibility before recording transactions.

## How to test
1. php artisan migrate:fresh --seed
2. Log in as admin@altatierra.test / Admin@12345
3. Navigate to /staff/dues
4. Verify homeowner with 12 unpaid months → "Good Standing"

Reviewer checklist

  • Does this match the linked issue / requirement?
  • Does the test suite still pass? (GitHub Actions will show if wired up)
  • Are the tests real assertions or just assertTrue(true)?
  • Is any business rule hardcoded instead of read from settings?
  • Is any policy decision invented by the code, rather than sourced from the HOA?
  • Are there edge cases the author missed? (empty inputs, boundary conditions, inactive users)
  • Would I understand this code in 6 months with no context?
Respond to reviews in 24 hours. If you can't review, say so on the PR and reassign. Silent PRs are invisible PRs, and invisible PRs are dead.

07 Pitfalls we've already hit

Every one of these cost us time. Learn from them once.

Heredoc leakage into .php files

Pasting a bash cat > file.php <<'PHP' block into the terminal sometimes leaves the closing PHP inside the file.

Fix: always paste PHP content into VSCode, not the shell. Or run php -l file.php right after.

Class name collisions

Two files declaring class ExampleTest in the same namespace → fatal on load. Laravel's default Unit and Feature examples both use that class name, but different namespaces.

Fix: check namespaces with grep -rH '^namespace' tests/ after pasting test files.

Model attribute drift

DB column has DEFAULT TRUE but the factory doesn't set it → in-memory model has null → middleware rejects. Login worked, tests broke.

Fix: for any column with a DB default, mirror it in the model's $attributes AND the factory.

VSCode stale language server

Edited the file outside VSCode? The IDE still shows errors from the old version. modelVersionId frozen at a stale number = cache.

Fix: Ctrl+Shift+P → PHP: Restart Language Server.

Wrong tab, wrong file

Ctrl+A+Delete+Paste applies to the active tab, not the one you think. You can overwrite the wrong file and not notice.

Fix: glance at the tab title before pasting. Ctrl+Z undoes the paste in that tab only.

Migrations on the wrong DB

php artisan migrate:fresh against hoa_db wipes all seeded users. Only run against test DBs. Check phpunit.xml uses sqlite :memory:.

Fix: before php artisan test, verify grep DB_ phpunit.xml.

08 Emergency commands

For the "oh no" moments. Memorize the top three.

I broke something, give me back yesterday's code

# See what changed
git status
git diff

# Discard ALL uncommitted changes (dangerous — you can't undo this)
git restore .

# Discard changes to just one file
git restore app/Http/Controllers/Auth/LoginController.php

# Get back to a specific commit (only on your own branch)
git log --oneline -10              # find the hash
git reset --hard <hash>

I accidentally staged something I didn't want

git restore --staged path/to/file      # unstage, keep the file
git status                              # verify

My branch is behind main, I need to catch up

git fetch origin
git rebase origin/main
# Fix conflicts if any, then:
git add <resolved-file>
git rebase --continue

I committed my .env by accident

# STOP. Don't push.
git rm --cached .env
# Add .env to .gitignore, then:
git commit -m "chore: remove .env from tracking"

# If you already pushed, tell the team — everyone needs to rotate secrets.
Never git push --force to main. It rewrites shared history and breaks everyone else's local repo. --force is only acceptable on your own feature branch, and even then, announce it in the group chat first.
